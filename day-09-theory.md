## Виклад

### 1. Чому обмеження в базі, а не в коді (5 хв)

Почни з питання: **у програмі вже є перевірка, що вік не від'ємний. Навіщо ще й
у базі?**

Три причини:

1. **До бази звертається не одна програма.** Сайт, мобільний застосунок,
   адмінка, скрипт імпорту. Перевірка в одному місці не захищає від решти.
2. **Програму переписують, база живе довше.** Дані переживуть три версії коду.
3. **Помилка в коді пропустить сміття один раз — і воно там назавжди.** Ще
   гірше: за пів року ніхто не згадає, чому в базі є замовлення на клієнта, якого
   не існує.

Формула для запису: **обмеження — це правило, яке база не дасть порушити нікому.**

### 2. Шість обмежень (15 хв, головна частина)

Показуй кожне запитом і питанням «а що станеться без нього».

**`PRIMARY KEY`** — унікальність рядка. Одна таблиця — один первинний ключ.

```sql
CREATE TABLE Club.Members (
    ID INT PRIMARY KEY,
    ...
);
```

Без нього: два однакових рядки, і незрозуміло, який із них правити.

**`NOT NULL`** — поле обов'язкове.

```sql
LastName NVARCHAR(50) NOT NULL
```

Без нього: учасник без прізвища.

**`UNIQUE`** — значення не повторюється.

```sql
PhoneNumber NVARCHAR(20) UNIQUE
```

Без нього: двоє з одним телефоном — швидше за все, той самий записався двічі.

**`CHECK`** — умова на значення.

```sql
Age INT CHECK (Age >= 0)
Amount DECIMAL(10,2) CHECK (Amount > 0)
```

Без нього: вік −5, платіж на −100 гривень.

**`DEFAULT`** — значення, якщо не вказали.

```sql
Status NVARCHAR(50) DEFAULT N'Активний'
IsActive BIT DEFAULT 1
```

**`FOREIGN KEY`** — зв'язок із іншою таблицею:

```sql
CREATE TABLE Club.Payments (
    ID INT PRIMARY KEY,
    MemberID INT NOT NULL,
    Amount DECIMAL(10,2) NOT NULL CHECK (Amount > 0),
    FOREIGN KEY (MemberID) REFERENCES Club.Members(ID)
);
```

Без нього: платіж від учасника, якого не існує.

### 3. PRIMARY KEY проти UNIQUE (8 хв)

Обидва забезпечують унікальність, і клас їх плутає. Різниця:

| | `PRIMARY KEY` | `UNIQUE` |
|---|---|---|
| Скільки на таблицю | **один** | скільки завгодно |
| `NULL` дозволений | **ні** | так (одне значення `NULL`) |
| Призначення | ідентифікує рядок | забороняє дублі в стовпці |

Приклад, який усе ставить на місце: у таблиці учнів `ID` — первинний ключ, а
номер телефона — `UNIQUE`. Телефон унікальний, але **ідентифікувати учня по
телефону не годиться**: телефон можна змінити, а `ID` — ніколи.

Формула: **первинний ключ не має змінюватись за життя рядка.**

**Складений ключ** — коли ключем є пара стовпців:

```sql
CREATE TABLE Club.Attendance (
    MemberID INT,
    LessonDate DATE,
    PRIMARY KEY (MemberID, LessonDate)
);
```

Тут «учасник + дата» разом унікальні: один учасник не може двічі бути
відмічений на одному занятті. Саме так побудована таблиця `CustomerAddress` у
демо-базі — згадай день 6.

### 4. Сироти й каскади (7 хв)

**Запис-сирота** — рядок, який посилається на те, чого немає: платіж від
учасника №99, якого в таблиці учасників нема.

Зовнішній ключ не дасть цього створити. Але він же створює друге питання:
**що робити, коли видаляють учасника, у якого є платежі?**

Три варіанти поведінки:

| Варіант | Що робить | Коли годиться |
|---|---|---|
| Заборонити (за замовчуванням) | не дає видалити учасника, поки є платежі | майже завжди |
| `ON DELETE CASCADE` | видалить учасника **разом із його платежами** | коли дочірні дані без батька не мають сенсу |
| `ON DELETE SET NULL` | учасника видалить, у платежах поставить `NULL` | рідко |

⚠ Скажи про каскад прямо: він зручний і небезпечний. Одна команда `DELETE` може
за секунду знести пів бази, і скасувати це неможливо. Учні спробують каскад на
практиці — на своїй базі, не на демо.

**Консистентність** бази — це і є стан, коли всі правила виконуються: немає
дублів, немає сиріт, немає значень, що суперечать умовам. Тримається на трьох
речах: ключі, обмеження, **транзакції** (день 16).

### 5. Теорема CAP (7 хв)

Тут не потрібен формалізм. Потрібна одна ідея.

Уяви, що база лежить **не на одному сервері, а на трьох** — у Львові, Києві та
Варшаві. Кожен тримає копію даних.

Хочеться трьох речей одночасно:

- **C — Consistency.** Усі копії відповідають одне й те саме.
- **A — Availability.** Система відповідає, навіть якщо якийсь сервер зламався.
- **P — Partition tolerance.** Система працює, навіть якщо зв'язок між серверами
  обірвався.

**Теорема CAP кажe: одночасно всі три — неможливо.** Розподілена система мусить
обирати.

Розберіть це на прикладі. Зв'язок Львів–Київ обірвався. Приходить запит на
львівський сервер:

- **Обрали C:** сервер відповідає «не можу, я не впевнений, що мої дані свіжі».
  Дані правильні, але системи ніби немає.
- **Обрали A:** сервер відповідає тим, що має. Відповідь є, але вона може бути
  застарілою.

> Питання класу: **що вибрати для банківського переказу?** Consistency —
> краще «спробуйте пізніше», ніж списати гроші двічі. **А для лічильника
> лайків?** Availability — нехай число буде на секунду неточним, головне, щоб
> сторінка відкривалась.

Оце і є вся CAP на рівні 9 класу: **не буває системи без компромісу; питання не
«як зробити ідеально», а «чим ми готові платити».** Зв'яжи з днем 5: саме тому
NoSQL часто вибирає A, а реляційні бази — C.

## ⚠ Що піде не так

| Симптом | Причина | Що робити |
|---|---|---|
| «`UNIQUE` і `PRIMARY KEY` — одне й те саме» | схожі на вигляд | таблиця з розділу 3 + приклад із телефоном |
| `The INSERT statement conflicted with the FOREIGN KEY constraint` | вставляють дочірній рядок раніше за батьківський | спершу учасник, потім його платіж |
| `Cannot insert duplicate key` | той самий `ID` | подивитись, що вже є в таблиці |
| `The DELETE statement conflicted with the REFERENCE constraint` | видаляють батька, у якого є діти | це **правильна** робота бази, не помилка |
| Клас вважає CAP абстракцією | немає прикладу | приклад із перериванням зв'язку, розділ 5 |

## Урок 2 — практика: відповіді й критерії

Учнівський файл: `day-09-practice.md`. Працюють у **своїй** базі `School97` із
дня 8. Якщо в когось її немає — створити заново, це 2 хвилини (день 8, крок 3).

### Крок 1. Перебудувати таблиці з обмеженнями

Очікуваний результат:

```sql
DROP TABLE IF EXISTS Club.Payments;
DROP TABLE IF EXISTS Club.Members;

CREATE TABLE Club.Members (
    ID INT PRIMARY KEY,
    LastName NVARCHAR(50) NOT NULL,
    FirstName NVARCHAR(50) NOT NULL,
    BirthDate DATE NULL,
    Phone NVARCHAR(20) UNIQUE,
    IsActive BIT NOT NULL DEFAULT 1
);

CREATE TABLE Club.Payments (
    ID INT PRIMARY KEY,
    MemberID INT NOT NULL,
    Amount DECIMAL(10,2) NOT NULL CHECK (Amount > 0),
    PaidAt DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    FOREIGN KEY (MemberID) REFERENCES Club.Members(ID)
);
```

⚠ **Порядок видалення важливий:** спершу `Payments`, потім `Members`. Навпаки
база не дасть — і це саме те, що учень мусить побачити. Хай спробує в
неправильному порядку й прочитає помилку.

### Крок 2. Спробувати порушити кожне обмеження

Очікувані помилки — учень мусить виписати текст кожної:

| Спроба | Помилка |
|---|---|
| два рядки з однаковим `ID` | `Violation of PRIMARY KEY constraint` |
| учасник без прізвища | `Cannot insert the value NULL into column 'LastName'` |
| два однакові телефони | `Violation of UNIQUE KEY constraint` |
| платіж на −100 | `The INSERT statement conflicted with the CHECK constraint` |
| платіж від учасника №99 | `conflicted with the FOREIGN KEY constraint` |
| вставка без `IsActive` | **помилки немає**, підставилось `1` |

Останній рядок важливий: `DEFAULT` — єдине з шести обмежень, яке **не
забороняє**, а **допомагає**.

### Крок 3. Сироти й каскад

Послідовність: видалити учасника, у якого є платежі → база не дає → перебудувати
зовнішній ключ із `ON DELETE CASCADE` → видалити знову → платежі зникли самі.

Обов'язковий висновок письмово: **чим каскад небезпечний**. Очікується щось на
кшталт «одна команда видалила дані з двох таблиць, і я цього не бачив».

### Крок 4. Складений ключ

```sql
CREATE TABLE Club.Attendance (
    MemberID INT NOT NULL,
    LessonDate DATE NOT NULL,
    PRIMARY KEY (MemberID, LessonDate),
    FOREIGN KEY (MemberID) REFERENCES Club.Members(ID)
);
```

Перевірка: двічі відмітити того самого учасника на ту саму дату → помилка. Того
самого на іншу дату → нормально.

### Крок 5. CAP на прикладі

Три ситуації в учнівському файлі. Очікувані відповіді:

| Ситуація | Вибір | Чому |
|---|---|---|
| Переказ грошей | **C** | краще відмовити, ніж списати двічі |
| Лічильник переглядів відео | **A** | неточне число нікому не шкодить |
| Бронювання останнього місця в поїзді | **C** | два пасажири на одному місці — гірше за відмову |

⚠ Оцінюється **обґрунтування, не буква**. Учень, який вибрав A для бронювання й
написав «краще продати двічі й потім вибачитись, ніж втратити всі продажі при
збою» — дав змістовну відповідь, хоча в реальності так не роблять. Це вартий
розбору аргумент.
