## Виклад

### 1. Транзакції (14 хв, головна частина)

Почни з задачі, яку клас уже чув на дні 5, але тепер її можна розв'язати.

**Переказ 100 гривень з рахунку 1 на рахунок 2 — це дві команди:**

```sql
UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;
```

Питання класу: **що станеться, якщо між ними вибило світло?** Сто гривень
зникло з системи. У першого немає, до другого не дійшло.

⚠ Це не гіпотетична проблема — це причина, через яку транзакції взагалі
придумали.

**Транзакція** — група команд, яка виконується **як одна неподільна операція**:
або всі, або жодна.

```sql
BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;

COMMIT TRANSACTION;     -- зафіксувати обидві зміни
```

Якщо щось не так — **скасувати все**:

```sql
ROLLBACK TRANSACTION;   -- відкотити, ніби нічого не було
```

Сучасний спосіб обробки помилок у T-SQL:

```sql
BEGIN TRY
    BEGIN TRANSACTION;

    UPDATE Accounts SET Balance = Balance - 100 WHERE AccountID = 1;
    UPDATE Accounts SET Balance = Balance + 100 WHERE AccountID = 2;

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    PRINT N'Помилка, зміни скасовано';
END CATCH;
```

⚠ У старих посібниках зустрінеться `IF @@ERROR <> 0 ROLLBACK`. Це працює, але
`TRY … CATCH` надійніший і читабельніший — саме його й варто давати.

🖥 **Найкраща демонстрація уроку, роби її обов'язково.** На своїй базі:

```sql
BEGIN TRANSACTION;
DELETE FROM Club.Members;              -- видалили ВСЕ
SELECT * FROM Club.Members;            -- порожньо!
ROLLBACK TRANSACTION;
SELECT * FROM Club.Members;            -- усе на місці
```

Клас бачить, як видалені дані **повертаються**. Після одинадцяти днів
попереджень «скасувати `DELETE` неможливо» це справляє враження — і одразу треба
сказати чому: неможливо скасувати `DELETE`, який уже **зафіксовано**. Усередині
відкритої транзакції — можна.

⚠ І одразу друге попередження: відкрита транзакція **тримає блокування**. Поки
ти не зробив `COMMIT` або `ROLLBACK`, інші не можуть працювати з цими рядками.
Забута відкрита транзакція в SSMS — класична причина «база висить». Якщо на
практиці в когось запит не відповідає — швидше за все, у сусідньому вікні
відкрита транзакція.

### 2. ACID (6 хв)

Чотири властивості, кожну одним реченням і одним прикладом:

| Літера | Що означає | Приклад |
|---|---|---|
| **A** — Atomicity, атомарність | або всі команди, або жодна | переказ грошей не буває наполовину |
| **C** — Consistency, узгодженість | після транзакції всі правила бази виконані | зовнішні ключі й `CHECK` не порушені (день 9) |
| **I** — Isolation, ізольованість | інші не бачать половини твоєї роботи | ніхто не побачить, що гроші «в дорозі» |
| **D** — Durability, довговічність | після `COMMIT` дані виживуть навіть при збою | вибило світло після `COMMIT` — переказ на місці |

Зв'яжи з днем 9: **саме через літеру `C` теорема CAP і використовує ту саму
букву.** Розподіленій системі доводиться вибирати між `C` і доступністю — а
одинокий сервер із транзакціями дає `C` без компромісів. Ось чому банк тримає
дані в реляційній базі.

### 3. Представлення — VIEW (10 хв)

**Представлення** — збережений запит, який виглядає й використовується як
таблиця. Своїх даних не має: щоразу, коли до нього звертаються, виконується
запит, що за ним стоїть.

```sql
CREATE VIEW SalesLT.ExpensiveProducts AS
SELECT Name, ListPrice, Color
FROM SalesLT.Product
WHERE ListPrice > 1000;
GO
```

Далі з ним працюють як зі звичайною таблицею:

```sql
SELECT * FROM SalesLT.ExpensiveProducts WHERE Color = 'Black';
SELECT COUNT(*) FROM SalesLT.ExpensiveProducts;
```

Дві причини використовувати:

1. **Спрощення.** Складний запит на три таблиці з групуванням написаний один
   раз. Далі всі пишуть `SELECT * FROM Звіт`.
2. **Безпека.** У таблиці працівників є зарплата. Створюємо представлення без
   цього стовпця й даємо доступ до представлення, а не до таблиці. Побачити
   зарплату фізично неможливо.

| | Таблиця | Представлення |
|---|---|---|
| Зберігає дані | так | **ні** |
| Займає місце | так | майже ні (лише текст запиту) |
| Дані актуальні | самі по собі | завжди свіжі, бо запит виконується щоразу |

> Питання класу: **дані в таблиці змінились. Чи треба оновлювати
> представлення?** Ні — воно не копія, а запит. Кожне звернення бере свіжі дані.
> Це принципова відмінність від `SELECT … INTO` (день 7), який робить саме копію
> й одразу застаріває.

### 4. Тригери (10 хв)

**Тригер** — процедура, яка виконується **сама**, у відповідь на `INSERT`,
`UPDATE` або `DELETE`.

```sql
CREATE TRIGGER Club.trgMemberInsert
ON Club.Members
AFTER INSERT
AS
BEGIN
    INSERT INTO Club.AuditLog (ChangeDate, Description)
    VALUES (GETDATE(), N'Додано нового учасника');
END;
GO
```

Тепер **кожна** вставка в `Members` сама допише рядок у журнал. Програміст, який
пише `INSERT`, може навіть не знати, що тригер існує.

Типи:

- **`AFTER`** — після операції. Журнал змін, перерахунок підсумків.
- **`INSTEAD OF`** — **замість** операції. Використовують здебільшого на
  представленнях, щоб зробити їх такими, у які можна писати.

⚠⚠ **Скажи це прямо, це головне про тригери.** Тригер — найпідступніша річ у
базі даних. Причини:

1. **Його не видно в коді.** Розробник виконує `INSERT` одного рядка, а
   змінюються три таблиці. У тексті його програми цього немає ніде.
2. **Тригери можуть викликати тригери.** Тригер на таблиці A пише в B, там свій
   тригер пише в C. Розібратись, чому одна вставка тривала три секунди, дуже
   важко.
3. **Помилка в тригері валить операцію**, яка з ним ніяк не пов'язана.

Практичне правило, яке варто дати: **тригери годяться для журналу змін
(аудиту), а бізнес-логіку краще тримати в коді програми або в процедурах**, де
її видно.

Зв'яжи з днем 9: `CHECK` і `FOREIGN KEY` роблять частину роботи, яку колись
робили тригерами — і роблять її прозоро. Якщо задачу можна закрити обмеженням,
тригер не потрібен.

### 5. Коментарі (3 хв)

```sql
SELECT * FROM SalesLT.Product;   -- однорядковий коментар

/* Багаторядковий.
   Використовується для довших пояснень
   або щоб тимчасово вимкнути частину запиту. */
```

Учні вже користувались коментарями всі одинадцять днів практики — тут просто
називаємо це своїм ім'ям і додаємо один прийом: **коментарем зручно тимчасово
вимкнути рядок запиту**, щоб перевірити, як він працює без нього. Наприклад
закоментувати `HAVING` і подивитись, скільки груп було до фільтрації.

## ⚠ Що піде не так

| Симптом | Причина | Що робити |
|---|---|---|
| Запити «висять», нічого не відповідає | забута відкрита транзакція в іншому вікні | знайти вікно, зробити `ROLLBACK`; попередити про це заздалегідь |
| `ROLLBACK` не спрацював | `COMMIT` уже виконано | після фіксації відкат неможливий — у цьому весь сенс `D` в ACID |
| `The COMMIT TRANSACTION request has no corresponding BEGIN` | `COMMIT` без `BEGIN` | перевірити, чи виділили весь блок мишкою |
| `CREATE VIEW must be the only statement in the batch` | немає `GO` | `GO` перед і після |
| Тригер спрацював не так, як чекали | тригери працюють на **набір** рядків, не на один | не заглиблюватись у 9 класі; сказати, що так буває |
| Хтось створив тригер на демо-базі й зламав її | тригери робимо **тільки на своїй базі** | відновити з `.bak` |

## Урок 2 — практика: відповіді й критерії

Учнівський файл: `day-16-practice.md`. Файл здачі — `day16.sql`.

⚠ **Тригери й транзакції з `DELETE` — тільки на власній базі `School97`.** На
демо-базі це швидко призводить до необхідності відновлення.

### Відповіді

**Крок 1. ROLLBACK повертає дані**

Послідовність із виклада (розділ 1). Обов'язковий висновок письмово: **`DELETE`
скасувати можна, поки транзакція не зафіксована.**

**Крок 2. COMMIT остаточний**

Той самий сценарій, але з `COMMIT` замість `ROLLBACK`, потім спроба
`ROLLBACK`. Учень мусить отримати помилку або побачити, що дані не повернулись,
і зв'язати це з літерою `D` в ACID.

**Крок 3. Переказ грошей**

```sql
CREATE TABLE Club.Accounts (ID INT PRIMARY KEY, Owner NVARCHAR(50), Balance DECIMAL(10,2));
INSERT INTO Club.Accounts VALUES (1, N'Іваненко', 500), (2, N'Петренко', 300);

BEGIN TRANSACTION;
UPDATE Club.Accounts SET Balance = Balance - 100 WHERE ID = 1;
UPDATE Club.Accounts SET Balance = Balance + 100 WHERE ID = 2;
COMMIT TRANSACTION;
```

Далі — «збій»: виконати лише перший `UPDATE`, подивитись суму по обох рахунках
(вона зменшилась на 100 — гроші зникли), потім `ROLLBACK`.

⚠ Ключове спостереження: **сума грошей у системі мусить не змінюватись.** Хай
учень перевіряє це запитом `SELECT SUM(Balance) FROM Club.Accounts;` до й після.
Це найкраща перевірка узгодженості, яку можна показати в 9 класі.

**Крок 4. Представлення**

```sql
CREATE VIEW SalesLT.vExpensive AS
SELECT Name, ListPrice, ISNULL(Color, N'не вказано') AS Колір
FROM SalesLT.Product WHERE ListPrice > 1000;
GO

SELECT * FROM SalesLT.vExpensive WHERE Колір = 'Black';
```

Далі перевірка «свіжості»: змінити ціну одного товару так, щоб він потрапив або
випав із представлення, і побачити, що представлення змінилось само.

⚠ Це головне спостереження кроку. Порівняй із `SELECT … INTO` з дня 7 — там
копія б залишилась старою.

**Крок 5. Тригер-журнал**

```sql
CREATE TABLE Club.AuditLog (
    ID INT IDENTITY PRIMARY KEY,
    ChangeDate DATETIME2 DEFAULT SYSDATETIME(),
    Description NVARCHAR(200)
);
GO

CREATE TRIGGER trgMemberInsert ON Club.Members AFTER INSERT
AS
BEGIN
    INSERT INTO Club.AuditLog (Description)
    VALUES (N'Додано учасника');
END;
GO
```

Учень вставляє двох учасників і бачить у журналі два рядки, яких не писав.

Обов'язкове питання: **чи є в твоєму `INSERT` хоч слово про журнал?** Немає. У
цьому і сила, і небезпека тригерів.
