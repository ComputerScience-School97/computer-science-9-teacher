## Мета дня

Учень розуміє, що індекс — це компроміс: швидше читання за рахунок повільнішого
запису й додаткового місця. Уміє додавати рядки пачками й оновлювати їх точно.

- назвати три ціни, які платять за індекс

## Виклад

### 1. Що таке індекс (6 хв)

Аналогія, з якої варто починати — **підручник**. Треба знайти, де в ньому
згадується слово «транзакція». Два способи:

- гортати всі 300 сторінок по черзі — це **повне сканування таблиці**
- відкрити предметний покажчик у кінці, знайти слово, побачити «с. 148» — це
  **пошук за індексом**

Індекс у базі — окрема структура, у якій значення стовпця вже впорядковані й
поруч лежить вказівка, де саме шукати рядок.

Питання, яке варто задати одразу: **скільком сторінок довелось надрукувати
більше, щоб у книзі був покажчик?** Ось звідси й почнеться розмова про ціну.

### 2. Кластеризований і некластеризований (10 хв, головна частина)

**Кластеризований індекс** визначає **фізичний порядок рядків** у таблиці. Тобто
рядки лежать на диску вже впорядковані за цим стовпцем.

Тому **на таблицю він може бути тільки один** — дані не можна фізично
впорядкувати двома способами одночасно.

Аналогія: **порядок слів у самому словнику.** Слова в словнику лежать за
алфавітом. Вони не можуть одночасно лежати і за алфавітом, і за довжиною.

**Некластеризований індекс** — це окрема структура «збоку»: значення
впорядковані в ній, а сам рядок лежить там, де лежав. Таких індексів може бути
багато.

Аналогія: **предметний покажчик у кінці книги.** Порядок сторінок він не
змінює. І покажчиків може бути кілька — предметний, іменний, географічний.

| | Кластеризований | Некластеризований |
|---|---|---|
| Скільки на таблицю | **один** | багато |
| Змінює порядок рядків | так | ні |
| Займає багато місця | ні (це самі дані) | так (окрема копія стовпця) |
| Добрий для | діапазонів, сортувань, `BETWEEN` | точного пошуку за значенням |

⚠ У SQL Server `PRIMARY KEY` за замовчуванням **створює кластеризований
індекс**. Тобто учні вже створили індекси на дні 8 і 9, просто не знали про це.
Скажи це вголос — воно добре зшиває тему.

### 3. Ціна індексу (8 хв)

Головна думка всього уроку: **індекс — не безкоштовне прискорення.**

Три ціни:

1. **Місце.** Кожен некластеризований індекс — це додаткова копія стовпця з
   покажчиками.
2. **Повільніший запис.** При кожному `INSERT`, `UPDATE`, `DELETE` база мусить
   оновити не лише дані, а й **усі індекси** цієї таблиці. П'ять індексів —
   п'ять додаткових оновлень на кожну вставку.
3. **Обслуговування.** Індекси фрагментуються, їх треба перебудовувати. Погано
   вибраний індекс не використовується взагалі, а гальмувати не перестає.

> Питання класу: **у таблицю щосекунди пишуть тисячу рядків із датчиків, а
> читають раз на день. Скільки індексів там треба?** Якнайменше. І навпаки: у
> каталозі товарів, який читають мільйони разів і змінюють раз на тиждень,
> індекси виправдані.

Формула для запису: **індекс прискорює читання й уповільнює запис.** Вибір
залежить від того, чого в системі більше.

### 4. INSERT (9 хв)

Один рядок:

```sql
INSERT INTO Club.Members (ID, LastName, FirstName, IsActive)
VALUES (10, N'Іваненко', N'Богдан', 1);
```

**Кілька рядків одним запитом** — так робити і швидше, і зручніше:

```sql
INSERT INTO Club.Members (ID, LastName, FirstName, IsActive)
VALUES
    (11, N'Петренко', N'Софія', 1),
    (12, N'Коваль',   N'Тарас', 1),
    (13, N'Шевчук',   N'Марія', 0);
```

⚠ Важлива деталь: якщо **один** рядок із цієї пачки порушує обмеження, **не
вставиться жодний**. Уся команда — одна операція. Це перший дотик до ідеї
транзакції (день 16), і його варто назвати.

**`DEFAULT`** працює саме тут: стовпець, який має значення за замовчуванням,
можна не перелічувати, і він заповниться сам.

Перелік стовпців можна не писати — але не варто:

```sql
INSERT INTO Club.Members VALUES (14, N'Мороз', N'Іван', NULL, NULL, 1);
```

Тут порядок значень мусить точно збігатися з порядком стовпців у таблиці. Якщо
хтось додасть у таблицю стовпець, запит зламається або, гірше, запише дані не в
ті поля.

### 5. UPDATE і головний прийом (9 хв)

```sql
UPDATE Club.Members
SET IsActive = 0
WHERE ID = 12;
```

Можна змінити кілька стовпців за раз:

```sql
UPDATE Club.Members
SET IsActive = 0, Phone = NULL
WHERE BirthDate < '2009-01-01';
```

⚠⚠ **`UPDATE` без `WHERE` змінює всю таблицю.** Скажи це знову, вголос — цей
урок останній, де це можна безпечно повторити перед днем 11, коли учні почнуть
масово змінювати свої дані.

**Прийом, який варто дати як обов'язкове правило:**

```sql
-- КРОК 1: подивитись, кого зачепить
SELECT * FROM Club.Members WHERE BirthDate < '2009-01-01';

-- КРОК 2: якщо саме ті рядки — той самий WHERE у UPDATE
UPDATE Club.Members SET IsActive = 0 WHERE BirthDate < '2009-01-01';
```

Тобто: **спершу той самий фільтр у `SELECT`, і лише потім `UPDATE`.** Це
займає п'ять секунд і врятує від найдорожчої помилки в SQL. Дорослі
розробники роблять саме так на робочих базах.

Той самий прийом працює й для `DELETE` — про це буде день 11.

## ⚠ Що піде не так

| Симптом | Причина | Що робити |
|---|---|---|
| «Індекс — це завжди краще» | не видно ціни | розділ 3, питання про датчики |
| Клас не розуміє, чому кластеризований один | немає аналогії | порядок слів у словнику |
| `INSERT` пачкою впав, вставилось 0 рядків | одне значення порушило обмеження | так і має бути; шукати, яке саме |
| `UPDATE` змінив усі рядки | забуто `WHERE` | відновити базу; правило «спершу SELECT» |
| `Cannot insert explicit value for identity column` | у таблиці `IDENTITY` | не вказувати цей стовпець у `INSERT` |
| `String or binary data would be truncated` | текст довший за `NVARCHAR(n)` | збільшити `n` або скоротити значення |

## Урок 2 — практика: відповіді й критерії

Учнівський файл: `day-10-practice.md`. Файл здачі — `day10.sql`.

### Крок 1. Подивитись на наявні індекси

У дереві: `AdventureWorksLT → Tables → SalesLT.Product → Indexes`. Там уже є
кластеризований (по `ProductID`) і кілька некластеризованих — зокрема на `Name`
і `ProductNumber`, які мають `UNIQUE`.

⚠ Ключове спостереження: **індекси в цій базі не створював ніхто окремо** — вони
з'явилися разом із `PRIMARY KEY` і `UNIQUE`.

### Крок 2. План виконання запиту

```sql
-- увімкнути показ плану: Ctrl+M, потім виконати запит
SELECT * FROM SalesLT.Product WHERE ProductID = 707;      -- Index Seek
SELECT * FROM SalesLT.Product WHERE Color = 'Black';      -- Index Scan / Table Scan
```

Учень мусить побачити на вкладці `Execution plan` різні операції й записати їх
назви. Пояснення: **Seek** — база пішла прямо до потрібного рядка (є індекс),
**Scan** — переглянула всі (індексу немає).

⚠ На 295 рядках різниці в часі не буде видно, і це варто сказати одразу: сенс
кроку — побачити **різні способи**, а не різний час. На мільйоні рядків це була
б різниця між 0,01 с і 10 с.

### Крок 3. Створити свій індекс

```sql
CREATE NONCLUSTERED INDEX IX_Product_Color ON SalesLT.Product (Color);
```

Після цього повторити запит із `WHERE Color = 'Black'` і подивитись план знову.
Може змінитись на `Index Seek` — а може й не змінитись, бо оптимізатор вирішить,
що на такій маленькій таблиці простіше прочитати все. **Обидва результати
правильні**, і другий навіть цікавіший: база не зобов'язана користуватись
індексом, вона вибирає сама (згадай день 6, декларативність).

Наприкінці індекс видалити: `DROP INDEX IX_Product_Color ON SalesLT.Product;`

### Крок 4. INSERT пачкою

Очікується один `INSERT` із п'ятьма рядками у `Club.Members`.

Далі — навмисна помилка: у пачці з трьох рядків один із дублікатом `ID`.
Результат: **не вставився жоден**. Учень мусить перевірити це `SELECT`-ом і
записати висновок.

### Крок 5. UPDATE за правилом

Послідовність обов'язкова: `SELECT` із фільтром → порахувати рядки → той самий
фільтр у `UPDATE` → перевірити `SELECT`-ом.

⚠ У кроці 5.4 учні мусять навмисно виконати `UPDATE` **без** `WHERE` — але
**на своїй базі `School97`**, не на демо. Після цього побачити, що змінились усі
рядки, і зрозуміти, що скасувати це неможливо. Це найкорисніші тридцять секунд
блоку, і саме тому робиться на власних вигаданих даних.

Якщо хтось запустив таке на `AdventureWorksLT` — відновити з `.bak`, дві
хвилини, не драматизувати.
