## Виклад

### 1. 🖐 Постановка на дошці (5 хв)

Учні вже вміють: `SELECT AVG(ListPrice) FROM Product` → **одне число**.

Питання: **а якщо треба середню ціну окремо для чорних, окремо для червоних,
окремо для білих?**

Перше, що прийде класу в голову — написати три запити з різними `WHERE`. Хай
скажуть це вголос. Далі спитай: **а якщо кольорів не три, а сорок? А якщо
завтра з'явиться новий колір?**

Оце і є задача, яку розв'язує `GROUP BY`: **один запит, а результат — по одному
рядку на кожну групу.**

### 2. GROUP BY (13 хв, головна частина)

```sql
SELECT Color, AVG(ListPrice)
FROM SalesLT.Product
GROUP BY Color;
```

Механіка, яку варто намалювати на дошці: база **складає рядки в купки** за
однаковим значенням `Color`, а потім до кожної купки застосовує `AVG`.

```
Black:  [товар, товар, товар, …]  →  AVG → одне число
Red:    [товар, товар]            →  AVG → одне число
NULL:   [товар, товар, …]         →  AVG → одне число
```

⚠ Зверни увагу класу: **`NULL` теж утворює свою групу.** Товари без кольору
опиняться в одному рядку результату з порожнім `Color`.

Ще приклади:

```sql
SELECT Color, COUNT(*) AS Кількість FROM SalesLT.Product GROUP BY Color;
SELECT Size, MAX(ListPrice) FROM SalesLT.Product GROUP BY Size;
SELECT ProductCategoryID, COUNT(*), AVG(ListPrice)
FROM SalesLT.Product GROUP BY ProductCategoryID;
```

**Правило, без якого нічого не працює.** У `SELECT` при `GROUP BY` можуть бути
лише:

1. стовпці, за якими групуємо
2. агрегатні функції

```sql
-- ⚠ ПОМИЛКА
SELECT Color, Name, AVG(ListPrice) FROM SalesLT.Product GROUP BY Color;
```

Помилка: `Column 'Name' is invalid in the select list because it is not
contained in either an aggregate function or the GROUP BY clause`.

**Чому.** У групі «чорні» — 89 товарів із 89 різними назвами. Яку з них
показати в одному рядку? Питання не має відповіді, тому база й відмовляється.

🖥 Покажи цю помилку на проекторі навмисно. Її отримає весь клас на практиці, і
краще, щоб вони вже знали, що вона означає.

Групувати можна й за кількома стовпцями:

```sql
SELECT Color, Size, COUNT(*) FROM SalesLT.Product GROUP BY Color, Size;
```

Тоді група — це **комбінація** значень: «чорний + L» окремо від «чорний + M».

### 3. HAVING (10 хв, друга головна частина)

Задача: показати лише ті кольори, у яких **більше десяти** товарів.

Спроба, яку зробить клас:

```sql
SELECT Color, COUNT(*) FROM SalesLT.Product
WHERE COUNT(*) > 10                      -- ⚠ ПОМИЛКА
GROUP BY Color;
```

Правильно:

```sql
SELECT Color, COUNT(*) FROM SalesLT.Product
GROUP BY Color
HAVING COUNT(*) > 10;
```

**Різниця, яку треба донести через порядок виконання.** Напиши на дошці
послідовність:

```
1. FROM      — узяли таблицю
2. WHERE     — викинули непотрібні РЯДКИ
3. GROUP BY  — склали решту в групи
4. HAVING    — викинули непотрібні ГРУПИ
5. SELECT    — показали стовпці
6. ORDER BY  — відсортували
```

Звідси все стає очевидним:

- `WHERE` працює на кроці 2 — груп ще немає, тому `COUNT(*)` йому недоступний.
- `HAVING` працює на кроці 4 — групи вже є, агрегати вже пораховані.

Формула для запису: **`WHERE` фільтрує рядки до групування, `HAVING` фільтрує
групи після.**

Обидва разом в одному запиті — так і буває в реальних звітах:

```sql
SELECT Color, COUNT(*) AS Кількість
FROM SalesLT.Product
WHERE Weight IS NOT NULL      -- спершу відкидаємо товари без ваги
GROUP BY Color
HAVING COUNT(*) > 10          -- потім відкидаємо малі групи
ORDER BY Кількість DESC;
```

> Питання класу на розуміння: **чи можна те саме зробити двома `WHERE`?** Ні.
> І це добра нагода показати, що порядок виконання в SQL — не той, у якому
> написані слова. Запит **читається** зверху вниз, а **виконується** за схемою
> вище.

### 4. Копіювання даних (8 хв)

`SELECT … INTO` (день 7) створює **нову** таблицю. А коли таблиця вже існує:

```sql
INSERT INTO таблиця_призначення (стовпець1, стовпець2)
SELECT стовпець1, стовпець2 FROM таблиця_джерело WHERE умова;
```

Практичний приклад — архівування:

```sql
INSERT INTO SalesLT.Product_Archive (Name, ListPrice, SellEndDate)
SELECT Name, ListPrice, SellEndDate
FROM SalesLT.Product
WHERE SellEndDate < GETUTCDATE();
```

`GETUTCDATE()` дає поточний момент часу за UTC. Є ще `GETDATE()` — місцевий час
сервера.

⚠ Кількість і типи стовпців у `INSERT` і в `SELECT` мусять відповідати **за
порядком**, а не за назвою. Помилка тут тиха: якщо два текстові стовпці
переставити місцями, база спокійно запише прізвище в поле «ім'я».

| | `SELECT … INTO` | `INSERT INTO … SELECT` |
|---|---|---|
| Таблиця-приймач | створюється | мусить існувати |
| Структура | береться з запиту | своя, задана раніше |
| Коли потрібно | швидка копія на льоту | архів, накопичення, регулярне перенесення |

### 5. Тимчасові таблиці (7 хв)

Таблиця, яка живе до кінця сеансу й зникає сама.

```sql
CREATE TABLE #Temp (Color NVARCHAR(15), AvgPrice DECIMAL(10,2));
```

- `#Назва` — **локальна**: видна лише в цьому підключенні, зникає при
  від'єднанні.
- `##Назва` — **глобальна**: видна всім підключенням, зникає, коли останнє з
  них закриється.

Приклад, який показує, **навіщо** вона:

```sql
CREATE TABLE #Temp (Color NVARCHAR(15), AvgPrice DECIMAL(10,2));

INSERT INTO #Temp (Color, AvgPrice)
SELECT Color, AVG(ListPrice) FROM SalesLT.Product GROUP BY Color;

SELECT * FROM #Temp WHERE AvgPrice > 1000;
SELECT * FROM #Temp WHERE AvgPrice < 100;
```

Головна думка: **важке обчислення зробили один раз**, а результатом
скористались двічі. Без тимчасової таблиці довелось би двічі писати той самий
запит із `GROUP BY` і двічі його виконувати.

Аналогія з математики: виписав промiжний результат на чернетку, щоб не рахувати
його заново для другого й третього пункту задачі.

⚠ Скажи, що тимчасові таблиці займають пам'ять сервера, і залишати їх
«назавжди» не варто. Прибрати вручну: `DROP TABLE #Temp;`

## ⚠ Що піде не так

| Симптом | Причина | Що робити |
|---|---|---|
| `Column '…' is invalid in the select list` | зайвий стовпець при `GROUP BY` | правило з розділу 2: тільки групувальні стовпці й агрегати |
| `An aggregate may not appear in the WHERE clause` | `COUNT(*)` у `WHERE` | `HAVING` |
| У результаті `GROUP BY` є рядок із порожнім значенням | `NULL` утворює свою групу | так і має бути |
| `HAVING` без `GROUP BY` «щось повертає» | формально дозволено, працює по всій таблиці як одна група | не заглиблюватись, сказати, що так не пишуть |
| Дані після копіювання переставились між стовпцями | порядок у `INSERT` і `SELECT` не збігся | звірити по порядку, не за назвами |
| `#Temp` зникла | закрилось або перепідключилось вікно запиту | створити знову; це нормальна поведінка |

## Урок 2 — практика: відповіді й критерії

Учнівський файл: `day-14-practice.md`. Файл здачі — `day14.sql`.

> ⚠ Числа — для стандартної `AdventureWorksLT`. Прогони перед уроком.

### Відповіді

**Крок 1. Три запити проти одного**

Учень спершу пише три окремі запити з `WHERE Color = …`, потім один із
`GROUP BY`. Сенс — щоб він фізично відчув різницю в кількості роботи.

```sql
SELECT Color, COUNT(*) AS Кількість, AVG(ListPrice) AS Середня
FROM SalesLT.Product
GROUP BY Color
ORDER BY Кількість DESC;
```

**Крок 2. Помилка зі зайвим стовпцем**

```sql
SELECT Color, Name, AVG(ListPrice) FROM SalesLT.Product GROUP BY Color;
```

Учень мусить отримати помилку й **пояснити своїми словами**. Очікується:
«у групі багато різних назв, база не знає, яку показати».

Це головний крок практики на розуміння.

**Крок 3. Групування за двома стовпцями**

```sql
SELECT Color, Size, COUNT(*) FROM SalesLT.Product
GROUP BY Color, Size ORDER BY Color, Size;
```

Рядків стає більше, ніж при групуванні за одним стовпцем — бо групою стала
комбінація.

**Крок 4. HAVING**

```sql
-- 4.1
SELECT Color, COUNT(*) AS К FROM SalesLT.Product GROUP BY Color HAVING COUNT(*) > 10;

-- 4.2 категорії, де середня ціна понад 1000
SELECT ProductCategoryID, AVG(ListPrice) AS Середня
FROM SalesLT.Product GROUP BY ProductCategoryID HAVING AVG(ListPrice) > 1000;

-- 4.3 WHERE і HAVING разом
SELECT Color, COUNT(*) AS К FROM SalesLT.Product
WHERE ListPrice > 100 GROUP BY Color HAVING COUNT(*) > 5 ORDER BY К DESC;
```

⚠ У 4.3 попроси учня сказати, **скільки рядків відкинув `WHERE`, а скільки груп
відкинув `HAVING`**. Перевірити просто: виконати запит без `HAVING`, потім із
ним.

**Крок 5. Копіювання**

```sql
CREATE TABLE SalesLT.ProductArchive (
    Name NVARCHAR(50), ListPrice MONEY, Color NVARCHAR(15)
);

INSERT INTO SalesLT.ProductArchive (Name, ListPrice, Color)
SELECT Name, ListPrice, Color FROM SalesLT.Product WHERE ListPrice < 50;
```

Далі — навмисна помилка: переставити `Name` і `Color` місцями в `SELECT`.
Помилки не буде (обидва текстові), але в архіві кольори опиняться в стовпці
назв. **Це головне спостереження кроку**: база не захищає від помилки, якщо
типи сходяться.

**Крок 6. Тимчасова таблиця**

Послідовність із виклада. Питання «чому це краще за два запити з `GROUP BY`» —
очікувана відповідь: важке обчислення виконали один раз.

⚠ Хай учень перевірить, що станеться, якщо закрити вікно запиту й відкрити
нове: `#Temp` більше немає. Це найкраща демонстрація слова «тимчасова».

### Оцінювання

| Бали | Ознаки |
|---|---|
| 1–3 | `GROUP BY` за одним стовпцем, за зразком |
| 4–6 | Кроки 1–3; групування працює, помилку зі зайвим стовпцем отримано |
| 7–9 | Кроки 1–4; **`HAVING` застосовано правильно**, різницю з `WHERE` описано словами через порядок виконання |
| 10–12 | Усе + копіювання з поясненням тихої помилки зі порядком стовпців, або тимчасова таблиця з обґрунтуванням |
