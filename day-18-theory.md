## Виклад

### 1. 🖐 Таблиця проти документа (8 хв)

Найкращий початок — намалювати на дошці ті самі дані двома способами.

**Реляційно** (як робили весь блок) — щоб зберегти учня з гуртками, треба **три
таблиці**:

```
УЧНІ:    id=1, прізвище=Іваненко, клас=9-А
ГУРТКИ:  id=1, назва=шахи ; id=2, назва=робототехніка
ЗАПИСИ:  учень_id=1, гурток_id=1 ; учень_id=1, гурток_id=2
```

**Документо-орієнтовано** — усе в одному документі:

```json
{
  "прізвище": "Іваненко",
  "клас": "9-А",
  "гуртки": ["шахи", "робототехніка"],
  "телефон_батьків": "+380671234567"
}
```

Питання класу, по черзі:

1. **Який варіант простіший для читання «покажи все про Іваненка»?** Документ —
   одне звернення без жодного `JOIN`.
2. **А для питання «скільки всього учнів у шаховому гуртку»?** Реляційний —
   один `COUNT` із `JOIN`. У документах доведеться перебрати всі документи.
3. **Треба додати новому учневі поле «алергія». Що робити?** У таблиці —
   `ALTER TABLE`, і поле з'явиться у **всіх** рядків. У документі — просто
   дописати його **цьому** учневі, решти це не торкнеться.
4. **А що поганого в пункті 3?** Через рік у базі документи з різним набором
   полів, і невідомо, у кого що є. Гнучкість має ціну.

Оце і є вся суть різниці. Далі — конкретні системи.

### 2. MongoDB — документо-орієнтована (9 хв, головна частина)

Зберігає документи у форматі **BSON** — двійковому JSON. Схема не задана жорстко:
документи в одній колекції можуть мати різні поля.

Термінологія — обов'язково зіставити з тим, що клас знає:

| Реляційна база | MongoDB |
|---|---|
| таблиця | колекція |
| рядок | документ |
| стовпець | поле |
| `SELECT` | `find()` |
| `INSERT` | `insertOne()` |
| первинний ключ | `_id` (створюється сам) |

```javascript
// приблизний аналог SELECT * FROM Students WHERE Class = '9-А'
db.students.find({ "клас": "9-А" })

// вставка
db.students.insertOne({ "прізвище": "Петренко", "клас": "9-Б" })
```

⚠ Не вчимо синтаксис Mongo — показуємо, **що він існує й на що схожий**. Мета —
щоб слово «NoSQL» перестало бути порожнім.

**Де застосовують:** каталоги товарів (у різних товарів різні характеристики —
у книги автор, у футболки розмір), системи керування вмістом, профілі
користувачів, мобільні застосунки.

Приклад, який добре працює: **каталог інтернет-магазину.** У реляційній базі
доведеться або робити таблицю на кожен тип товару, або мати стовпці, порожні у
90% рядків. У документах кожен товар несе свої характеристики.

### 3. Redis — ключ-значення (7 хв)

Найпростіша модель: **ключ → значення**. І головна особливість — **дані
тримаються в оперативній пам'яті**, а не на диску.

Тому вона дуже швидка. Тому ж і головне обмеження: **пам'ять дорога й
скінченна**, а при вимкненні живлення дані можна втратити (є механізми
збереження на диск, але це не її призначення).

**Де застосовують:**

- **Кеш.** Результат важкого запиту (той самий `GROUP BY` із дня 14) лежить у
  Redis. Наступні тисячі відвідувачів отримують готову відповідь, не турбуючи
  основну базу. Це рівно та сама ідея, що тимчасова таблиця на дні 14, лише в
  масштабі всього сайту.
- **Сеанси користувачів** — хто зараз залогінений.
- **Черги повідомлень.**
- **Таблиці лідерів в іграх** — оновлюються щосекунди, і точність до останнього
  очка не критична.

> Питання класу: **чому не тримати в Redis усе, якщо він такий швидкий?** Бо
> оперативна пам'ять на сервері — це десятки гігабайтів, а диск — десятки
> терабайтів, і коштують вони на порядки різно. Плюс транзакцій, як у SQL, тут
> немає.

Зв'яжи з днем 9: Redis — класичний приклад системи, яка в CAP вибирає
**доступність**, а не строгу узгодженість.

### 4. Neo4j — графова (8 хв)

Дані — **вузли** (об'єкти) і **зв'язки** між ними, у яких теж є властивості.

Постав задачу, яку реляційна база розв'язує погано:

**«Знайди друзів друзів моїх друзів, які живуть у моєму місті.»**

- У реляційній базі це `JOIN` таблиці дружби **сам із собою тричі**. Запит
  величезний, працює повільно. А для «на п'ять кроків» — практично неможливо.
- У графовій це природний запит: іди по зв'язках `ДРУЖИТЬ` три кроки.

**Де застосовують:**

- соцмережі — «ви можете знати цю людину»
- рекомендації — «люди, які купили це, купували ще й те»
- **виявлення шахрайства** — найцікавіший приклад: троє клієнтів мають різні
  імена, але один телефон, спільну адресу й перекази між собою по колу. У
  таблицях таку схему майже не видно, у графі вона видна очима як замкнене
  кільце.
- логістика й маршрути, ІТ-мережі

### 5. Решта коротко (6 хв)

**CosmosDB** (Microsoft Azure) — хмарна **багатомодельна**: та сама база вміє
працювати як документна, ключ-значення, графова або колонкова. Розподілена по
всьому світу, тому дає малу затримку глобально.
Застосування: глобальні онлайн-ігри, платіжні системи, IoT.

**Cassandra** — колонкова, розподілена. Величезні обсяги, високa доступність.
Застосування: телеметрія, IoT, аналітика в компаніях із мільйонами користувачів.

**Firebase / Firestore** (Google) — хмарна база з **синхронізацією в реальному
часі**: змінилось на сервері — одразу з'явилось у всіх застосунках. Застосування:
мобільні застосунки, чати, спільні документи.

⚠ Не заглиблюйся. Достатньо, щоб назви не були порожніми.

### 6. Коли що вибирати (5 хв)

Таблиця, яку варто дати під запис:

| Ознака задачі | Тип бази |
|---|---|
| Гроші, оцінки, медичні записи — помилка дорога | **реляційна** |
| Дані строго однакової структури, багато зв'язків | **реляційна** |
| У кожного об'єкта свій набір полів | документо-орієнтована |
| Потрібна максимальна швидкість, дані тимчасові | ключ-значення |
| Головне в даних — **зв'язки**, а не самі об'єкти | графова |
| Тисячі записів на секунду, читання рідко | колонкова |

І головна теза, яку варто сказати вголос: **у справжніх системах
використовують кілька баз одночасно.** Інтернет-магазин: замовлення й платежі —
у реляційній (транзакції!), каталог товарів — у MongoDB, кошики й сеанси — у
Redis, рекомендації — у Neo4j. Це нормально, а не ознака поганого проєкту.

| «Тоді нащо ми вчили SQL» | розділ 6, останній абзац: використовують разом; і 90% робочих баз досі реляційні |
| Клас не розуміє графову базу | лише задача «друзі друзів»; без неї це абстракція |
| Урок перетворюється на список назв | тримати фокус на **типах**, не на брендах |
| Питання «а що швидше» | швидкість залежить від задачі; Redis швидший на читанні ключа й безпорадний на звіті |

### Крок 4. Схема шахрайства

Найцікавіший крок. Учень малює граф із трьох «клієнтів», у яких різні імена, але
спільний телефон і перекази по колу — і пише, чому в таблицях це важче побачити.

Очікувана відповідь: у таблицях це кілька окремих запитів, і схему видно лише
якщо знаєш, що саме шукати. На графі замкнене кільце видно очима.
