## Варіанти завдання

У учнівському файлі **три варіанти**. Роздай по рядах або дай вибір — важливо,
щоб сусіди мали різні.

Усі три однакові за складністю: **три таблиці, два зв'язки**.

| Варіант | Предметна область | Головна складність |
|---|---|---|
| А | Прокат велосипедів | зв'язок «клієнт ↔ велосипед» через прокати |

⚠ Варіант В трохи важчий — у ньому потрібна четверта таблиця або складений
ключ. Дай його сильнішим, або попередь, що трьох таблиць там може не хватити,
і це нормально.

## Урок 1: проєктування та створення

### Частина 1. Схема на папері (15 хв)

Що мусить бути:

- три таблиці з назвами
- перелік стовпців із типами
- **підкреслений первинний ключ** у кожній
- **стрілки зовнішніх ключів** між таблицями
- позначено, які поля обов'язкові

**Еталон для варіанта А (прокат велосипедів):**

```
КЛІЄНТИ
  ID            INT           ПЕРВИННИЙ КЛЮЧ
  Прізвище      NVARCHAR(50)  обов'язкове
  Імʼя          NVARCHAR(50)  обов'язкове
  Телефон       NVARCHAR(20)  унікальний
  ДатаРеєстрації DATE         за замовчуванням сьогодні

ВЕЛОСИПЕДИ
  ID            INT           ПЕРВИННИЙ КЛЮЧ
  Модель        NVARCHAR(50)  обов'язкове
  Тип           NVARCHAR(20)
  ЦінаЗаГодину  DECIMAL(10,2) обов'язкове, > 0
  Справний      BIT           за замовчуванням 1

ПРОКАТИ
  ID            INT           ПЕРВИННИЙ КЛЮЧ
  КлієнтID      INT → КЛІЄНТИ.ID     обов'язкове
  ВелосипедID   INT → ВЕЛОСИПЕДИ.ID  обов'язкове
  ВзятоКоли     DATETIME2     обов'язкове
  ПоверненоКоли DATETIME2     може бути NULL (ще не повернув)
  Сума          DECIMAL(10,2) > 0
```

⚠ **Найважливіше рішення в цій схемі** — те, що прокати виділені в окрему
таблицю. Учень, який спробує засунути прокат у таблицю клієнтів (стовпці
`велосипед1`, `велосипед2`), помилився концептуально. Це головний водорозділ
роботи.

⚠ Друге вартісне рішення — `ПоверненоКоли` дозволяє `NULL`. Це саме той випадок,
коли `NULL` осмислений: велосипед ще в прокаті. Хто це помітив і написав —
розуміє `NULL`.

**Типові помилки й скільки коштують:**

| Помилка | Наскільки серйозна |
|---|---|
| Немає окремої таблиці для зв'язку «багато-до-багатьох» | ключова, не вище 6 балів |
| Замість зовнішнього ключа дублюється прізвище або модель | ключова, не вище 6 балів |
| Немає первинного ключа в одній із таблиць | серйозна, −2 бали |
| Гроші у `FLOAT` або `INT` | −1 бал |
| Дата текстом (`NVARCHAR`) | −1 бал |
| Телефон числом (`INT`) | −1 бал |
| `VARCHAR` замість `NVARCHAR` для українського тексту | −1 бал |
| Не позначено обов'язковість полів | −1 бал |

### Частина 2. Створення в SQL Server (30 хв)

Що мусить бути у скрипті:

```sql
CREATE DATABASE BikeRental;
GO
USE BikeRental;
GO
CREATE SCHEMA Rental;
GO

CREATE TABLE Rental.Clients (
    ID INT PRIMARY KEY,
    LastName NVARCHAR(50) NOT NULL,
    FirstName NVARCHAR(50) NOT NULL,
    Phone NVARCHAR(20) UNIQUE,
    RegisteredAt DATE NOT NULL DEFAULT GETDATE()
);

CREATE TABLE Rental.Bikes (
    ID INT PRIMARY KEY,
    Model NVARCHAR(50) NOT NULL,
    BikeType NVARCHAR(20),
    PricePerHour DECIMAL(10,2) NOT NULL CHECK (PricePerHour > 0),
    IsWorking BIT NOT NULL DEFAULT 1
);

CREATE TABLE Rental.Rentals (
    ID INT PRIMARY KEY,
    ClientID INT NOT NULL,
    BikeID INT NOT NULL,
    TakenAt DATETIME2 NOT NULL,
    ReturnedAt DATETIME2 NULL,
    Total DECIMAL(10,2) CHECK (Total > 0),
    FOREIGN KEY (ClientID) REFERENCES Rental.Clients(ID),
    FOREIGN KEY (BikeID) REFERENCES Rental.Bikes(ID)
);
```

Обов'язкова частина — **демонстрація, що обмеження працюють**: три навмисні
порушення з виписаними помилками. Це швидкий і надійний спосіб побачити, чи
обмеження справді стоять, а не просто написані в коментарях.

## Урок 2: дані та запити

### Частина 3. Наповнення (10 хв)

Вимога: **5+ рядків у кожну таблицю**, `INSERT` пачками, правильний порядок
(батьківські таблиці спершу).

⚠ Дані мусять бути **осмислені для запитів частини 4**. Якщо всі прокати
однакової суми, запити з `MAX` і `GROUP BY` нічого не покажуть. У учнівському
файлі це прописано як вимога — стеж за нею, бо саме тут учні економлять.

### Частина 4. Запити — еталони

**4.1. Простий фільтр**

```sql
SELECT Model, PricePerHour FROM Rental.Bikes WHERE PricePerHour > 50;
```

**4.2. Сортування**

```sql
SELECT * FROM Rental.Bikes ORDER BY BikeType, PricePerHour DESC;
```

**4.3. Пошук за шаблоном**

```sql
SELECT * FROM Rental.Clients WHERE LastName LIKE N'І%';
```

**4.4. Агрегація**

```sql
SELECT COUNT(*) AS Прокатів, SUM(Total) AS Дохід, AVG(Total) AS Середній
FROM Rental.Rentals;
```

**4.5. Групування**

```sql
SELECT BikeType, COUNT(*) AS Кількість, AVG(PricePerHour) AS Середня
FROM Rental.Bikes GROUP BY BikeType;
```

**4.6. Групування з `HAVING`**

```sql
SELECT ClientID, COUNT(*) AS Прокатів
FROM Rental.Rentals GROUP BY ClientID HAVING COUNT(*) > 1;
```

**4.7. `JOIN` двох таблиць**

```sql
SELECT c.LastName, b.Model, r.TakenAt, r.Total
FROM Rental.Rentals AS r
INNER JOIN Rental.Clients AS c ON r.ClientID = c.ID
INNER JOIN Rental.Bikes AS b ON r.BikeID = b.ID
ORDER BY r.TakenAt DESC;
```

**4.8. `LEFT JOIN` + `IS NULL` — хто нічого не брав**

```sql
SELECT c.ID, c.LastName
FROM Rental.Clients AS c
LEFT JOIN Rental.Rentals AS r ON c.ID = r.ClientID
WHERE r.ClientID IS NULL;
```

⚠ **Це найважливіший запит роботи.** Він показує, чи зрозумів учень `JOIN` не
як «склеїти таблиці», а як інструмент відповіді на питання. Хто написав 4.8
самостійно — знає блок баз даних.

**4.9. Підзапит**

```sql
SELECT * FROM Rental.Rentals
WHERE Total > (SELECT AVG(Total) FROM Rental.Rentals);
```

**4.10. `NULL`-логіка — що зараз у прокаті**

```sql
SELECT b.Model, c.LastName, r.TakenAt
FROM Rental.Rentals AS r
INNER JOIN Rental.Bikes AS b ON r.BikeID = b.ID
INNER JOIN Rental.Clients AS c ON r.ClientID = c.ID
WHERE r.ReturnedAt IS NULL;
```

⚠ Другий за важливістю запит. Перевіряє, чи розуміє учень, що `NULL` тут
**несе зміст** — «ще не повернуто», а не «дані забули заповнити».

**4.11. `UPDATE` за правилом**

Мусить бути `SELECT` перед `UPDATE` із тим самим `WHERE`. Якщо `SELECT` немає —
знімай бал навіть за правильний `UPDATE`: правило проходило через увесь блок.

**4.12. Транзакція**

```sql
BEGIN TRANSACTION;
DELETE FROM Rental.Rentals WHERE ID = 1;
SELECT COUNT(*) FROM Rental.Rentals;
ROLLBACK TRANSACTION;
SELECT COUNT(*) FROM Rental.Rentals;
```

## Критерії оцінювання

| Бали | Ознаки |
|---|---|
| **1–3** | Схема намальована частково. У SQL Server створено 1–2 таблиці. Зв'язків немає. Запити — 1–2 найпростіші, за зразком |
| **4–6** | Три таблиці створено, дані вставлено. **Але:** немає справжнього зовнішнього ключа, або дублюється текст замість зв'язку, або обмежень майже немає. Запити 4.1–4.5 |
| **7–9** | Схема правильна: ключі, зв'язки, розумні типи. Обмеження стоять і продемонстровано, що працюють. Дані осмислені. Запити 4.1–4.7 і 4.11 із дотриманням правила «спершу `SELECT`» |
| **10–12** | Усе вище **плюс щонайменше два з трьох:** правильний `LEFT JOIN + IS NULL` (4.8), правильна робота з `NULL` як зі змістом (4.10), підзапит (4.9) або транзакція (4.12). Обґрунтовано вибір типів даних |

### Швидка перевірка — три речі

Якщо перевіряєш 25 робіт і часу мало, дивись на це:

1. **Чи є справжній `FOREIGN KEY`** і чи він працює (є демонстрація порушення)?
2. **Чи є запит 4.8** (`LEFT JOIN + IS NULL`)?
3. **Чи стоїть `SELECT` перед `UPDATE`** у частині 4.11?

Ці три ознаки розводять роботи точніше за все інше. Перша відділяє 6 від 7,
друга — 9 від 10, третя показує, чи закріпились навички, а не лише знання.
